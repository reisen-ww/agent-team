# AGENTEAM

**面向 Codex 的团队协作 Skill**：从理解需求、组织代理，到验收成果和恢复长任务，用一套可裁切的协作规则帮助团队持续交付。

用户作为目标与授权的决定者；直接对接用户的 AI 担任技术经理，负责弄清楚要做什么、提出方案、组织工作和检查结果。团队可以只有一个主管与执行者，也可以根据任务增加部门和执行组。

> AGENTEAM 是一套 Skill 和配套示例，不是多代理调度服务器、权限系统或安全沙箱。能否创建代理、计费限额是否强制执行、消息能否唤醒接收者，都取决于实际运行环境。

当前源码的 Skill 版本为 **0.7.0**，许可证为 **AGPL-3.0-or-later**。

## 它适合什么任务？

- **新项目或模糊需求**：技术经理与用户对齐使用场景、边界、验收方式和成本安排，再确认本轮实施范围。
- **需要分工的长任务**：组织编码、研究、审查或排障，明确每项成果的负责人、依赖、权限与验收方式。
- **推进中出现偏差或积压**：回看原目标和实际产物，调整工作顺序、并行程度或解决路线。
- **暂停、交接或上下文压缩后恢复**：核对有效需求、决定、已完成成果和在途工作，继续尚未完成的部分。

明确、短小的任务可以由当前会话直接处理；讨论规则也不会自动启动团队。

## 安装

仓库地址：<https://github.com/reisen-ww/AGENTEAM>。仓库根目录就是一个完整的 Skill，SKILL.md 与 references/、examples/ 等目录应保持在一起。

将仓库克隆或复制到当前 Codex 环境使用的 Skills 目录，并确保目标目录叫 agent-team。例如，在使用默认 Codex 目录的 Windows PowerShell 中：

~~~powershell
New-Item -ItemType Directory -Force -Path "$env:USERPROFILE\.codex\skills" | Out-Null
git clone https://github.com/reisen-ww/AGENTEAM.git "$env:USERPROFILE\.codex\skills\agent-team"
~~~

此命令适用于目标目录尚不存在的情况；已有安装时，先检查其来源和本地改动，再选择合适的更新方式。若使用自定义 CODEX_HOME、项目级 Skills 或其他宿主，请使用该环境实际配置的 Skills 路径。克隆取得仓库远端当前版本；与尚未发布的本地改动可能不同。

安装后在 Codex 中显式调用 $agent-team。若未出现在当前会话的 Skill 列表中，检查目录和 SKILL.md，并按照当前环境的方式刷新或重新启动会话。

## 快速开始

在自己的项目中，可以这样开始一轮需求对齐：

~~~text
$agent-team
我想做一个内部工具，帮助团队整理用户反馈并按问题分类。
请先和我对齐目标、使用场景、验收方式和本轮范围，
再提出是否需要团队、如何分工以及成本取舍。
现在先不要开始实施。
~~~

技术经理会利用已有资料核对前提，集中提出影响成果的缺口，并整理目标、范围、验收和团队建议。用户确认本轮实施范围及重要安排后，再按当前工具与授权开展工作。

任务已经足够明确时，可以直接说明目标、交付物、允许修改的范围及必要的验收条件。需要继续已有项目时，给出需求、决定和当前进度的位置，先恢复事实再安排下一步。

## 团队怎样协作？

### 角色可以裁切

| 角色 | 主要责任 |
|---|---|
| 用户 / PM | 确定目标、重要偏好、实施范围与授权，并提供业务反馈 |
| 技术经理 | 对接用户、理解需求、规划整体交付、协调跨领域问题并负责技术验收 |
| 部门主管 | 负责领域方案、工作拆分、跨组依赖与部门验收 |
| 执行组负责人 | 分配工作包、审查交付和证据、安排组内集成 |
| 执行者 | 在授权范围内实施、自查自测，提交成果、证据和未解决问题 |

这些是责任划分，不要求固定模型名称或人数。一个人或代理可以兼任多个角色，例如“技术经理兼主管 → 执行者”，也可以使用“部门主管 → 执行组负责人 → 执行者”。裁切层级时，原本的需求对齐、集成和验收职责仍要有人承担。

Astra、Sol、Terra、DS 可以作为角色映射的例子，但本 Skill 不把它们当作必需模型，也不根据名称、价格或组织图断言实际能力。选型与并发应结合任务、可用工具、用户授权及实际结果判断。

### 从任务到交付

1. **对齐目标**：用户和技术经理确认要解决的问题、必要结果、禁止事项和验收方法。
2. **划分工作**：每个工作包明确负责人、输入版本、允许范围、依赖、交付位置和验收方式。
3. **实施与协调**：执行者在授权范围内推进；成员可以直接核对事实和接口。涉及目标、权限或公共契约的变化，交有决定权的人处理。
4. **检查与集成**：执行者自查自测，直属主管核对相关要求、关键产物和原始证据；指定的集成人验证组合后的成果。
5. **交付或恢复**：区分已完成、未完成和未知事项；保留原需求、决定与证据入口，方便暂停后接续。

默认不为每次执行者交付自动建立独立审查树。用户、项目规则或风险要求独立复核时，安排未参与被审实施的人员或代理，并计入实际资源。只有当前面向用户的负责人使用面向用户的提问工具；其他成员的问题经负责人处理。

### 关注成果和总投入

团队以可验收、可集成的成果判断进度，同时考虑完成时间、实际费用、等待、返工和主管介入。文件数量、消息数量或成员是否忙碌，本身都不能证明取得了成果。

预计完成时间和普通检查点用于发现偏差、判断是否继续或换路，不自动变成停工和逐级审批。执行者与主管可以在既有授权范围内调整方法、顺序和资源分配；用户明确的预算、权限和硬截止仍需遵守。默认不设适用于所有任务的固定工具调用次数。

### 组间通信

消息统一交代用途、对象与版本、所需动作和依据；建议、求决、有效决定、交付及验收分开表达。接收者核对相关原文和状态，明确且已授权的任务直接推进，普通消息不增加“收到、复述、再批准”的回合。完整正文与证据保存在双方可访问的位置，关键约束不因摘要而丢失。

成员可直接协商事实、接口和依赖，改变他组承诺仍交有决定权的人。只通知受影响者；技术经理处理关键决定，不收所有日常同步。语义规则、例子和验证边界见 [记录与通信](references/coordination.md#消息与插队) 与 [通信验证示例](examples/communication-check/README.md)。统一格式不证明模型理解一致或自动降低成本。

## 试一试：一个主管与两个执行者

[小团队示例](examples/small-team/README.md) 用订单汇总任务展示工作包、组合验收、需求变更、重复消息和暂停恢复。示例记录是虚构演练数据，不代表已经运行过真实团队或通过生产验收。

可在仓库根目录运行离线记录检查和现有测试：

~~~sh
python -B scripts/check_run.py examples/small-team/records/01-accepted-r1.json
python -B scripts/check_run.py examples/small-team/records/02-impact-pending.json
python -B scripts/check_run.py examples/small-team/records/03-accepted-r2.json
python -B -m unittest discover -s tests -v
~~~

脚本需要 Python 3.10+，使用标准库。检查器只读取示例 JSON 并检查部分记录一致性；它不会派工或执行记录中的动作，也不能证明实际授权、真实费用、代理行为或操作系统隔离。示例 02 即使检查通过，表示的是“待复核状态记录一致”，不是任务已完成。

如果希望用真实代理开展演练，应先确认实际工具、人员形式、权限、预算和验收方式；示例中的角色与任务本身不构成现实授权。

## 能力边界

Skill 提供规则与交接方式，不会因安装而自动创建团队、后台巡检、权限控制或费用硬上限。独立聊天与原生子代理是不同的运行形态，是否可用以当前工具和用户授权为准。

文件记录可以帮助追溯，但文件写入本身不等于消息送达、任务已执行或暂停已生效；真实防重、停止、身份认证和资源控制需要环境提供相应能力。规则和示例也不能保证长任务永不偏差或在所有项目中节省成本。

## 版本与迁移

- **0.7.0**：补充组间与上下级统一消息语义、用途对应的接收行为、原文/版本绑定、职责相关信息和低成本协商；包含验证设计及限制，不宣称跨模型理解或长期效率已获得保证。
- **0.6.1**：区分预计时间、检查点和硬边界；强调自主推进、范围内调配，以及以可验收成果与总投入判断效率。该调整尚不能证明长期提速或降低费用。
- **0.6.0**：增加原目标、阶段成果、方向校准与辅助工作收敛的规则和通用情境材料。
- **0.5.0**：补充动作去重、需求变更后的验收影响、等待环、度量和可复现示例。
- **0.4.0**：存在早期 MIT 分发包与后续 AGPL 仓库快照；引用历史时应同时记录来源与指纹，避免仅凭版本号判断许可。

更新 Skill 不会自动更新已运行的代理或会话。切换版本时应核对有效规则、需求、成员状态和文件归属；不要由此自行重派工作或解除暂停。

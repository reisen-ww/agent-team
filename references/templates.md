# 最小记录模板

选用缺少的字段，合并进已有项目记录；不要机械复制成多套文件。下列记录不是可执行调度配置，未知值不能自动当作获准。

## 运行约定

```yaml
run_id: example-run
task_kind: coding
mode: small-team
protocol: {location: project-defined, version: null, fingerprint: null}
requirements: {location: project-defined, revision: R1}
authorization: {source: human-confirmation, scope: this-run}
user_interface_owner: current-chat
roles: {}  # 记录实际人员/会话及角色合并、模型选择；不填虚构ID
shared_records: project-defined
capacity: {max_members: null, max_active_requests: null}
budget: {unit: null, limit: null, source: null, scope: null, counter_owner: null, enforcement: agent-only}
timing: {expected_completion: null, checkpoint: null, hard_deadline: null, hard_deadline_source: null}
delegated_adjustments: null  # 已授权的继续、方法调整与资源调配范围
rework: {global_batch_limit: null, per_worker_limit: null, counter_owner: null}
review_mode: supervisor-plus-agreed-verification
integration: {executor: null, acceptance_owner: null}
notifications: exceptions-only
resume_owner: user-interface-owner
```

null 表示尚未约定，不是无限资源或已获授权。是否需要该字段按任务判断；影响派工的关键值未明确时不派相应工作。没有 Team 就无需填写成员/并发字段。时间值说明时区或起算点；预计完成与检查点用于判断进展，不自动停工。硬截止只有在来源和范围明确时才作为停止边界；缺省不代表要求 PM 人为补一个期限。预算来源规定是否必须遵守，enforcement 仅说明依靠代理还是有已核实的宿主执行能力。

## 工作包

```text
任务ID / 原需求版本 / 结果负责人 / 实施拥有者
目标与完成条件
对 PM 原目标的贡献、原文入口；硬要求 / 可替换的方法 / 待证假设
输入、接口、依赖产物ID/版本、需求ID/版本和已知假设
允许读写范围、独占资源和禁止事项
可自行决定 / 需升级的事项
验证方式、交付位置、预算和停止条件
问题交给谁；谁执行集成与验收
长任务：下个可验收成果或关键证据、预计时间/检查点及负责人
继续与换路线的决定权、无进展时的动作；适用的硬截止/总预算及其来源
```

## 交付/验收卡

```text
任务/需求版本；产物路径及提交/指纹；采用的直接输入版本
本阶段推进了哪条原目标；实际成果/排除的假设；该工作包是否仍有必要
测试作者、执行者、验收者与各自覆盖范围
实际命令/方法、环境、原始日志、结果
首次失败和必要修复；引用全局返工batch_id
已满足、未满足、未知和待用户反馈项
当前状态、下一推进人和恢复条件；变更影响、待复核项及无影响依据
需要评价效率时：实际交付经过时间、已知费用、审查/集成/外部等待、返工与主管介入
```

沿用已有日志和阶段记录取得上述信息，未知值明确未知。普通工具次数和预估偏差不单独代表效率或额度合规；具体判断见 [调度](scheduling.md)。不要求每次调用填写一张卡。

未完成/待决字段只列仍缺条件的实际事项，并写明影响、下一推进人和解除条件。已经处理的失效摘要、重复投递或明确拒绝可按交接需要说明，不自动计作未完成；候选建议不自动成为待办。拒绝某个动作后若原目标仍有缺口，应保留那个缺口。可在已有记录中分别写“已处理”“待条件”“候选”，不要求新增文件或状态平台。

## 通知

以下是共同语义，沿用现有工具和记录表达即可；不是所有消息都需复制整张表。使用规则、效力判断与接收行为见 [消息与插队](coordination.md#消息与插队)。已有可信工具元数据包含的发收对象无需重复抄写。

```text
用途与重点：本次是知会、核对/求决、派工/变更、交付、决定/验收还是暂停/恢复；发生了什么及影响
对象与版本：任务、需求/接口/产物及适用版本，与接收人的工作关系
所需动作：谁做什么、谁推进下一步；必要时注明预期回应或真实硬截止
依据与边界：原决定、工作包、完整正文、证据入口；相关硬限制显著写明
```

按用途补必要内容：

- 核对/求决：事实与假设、具体缺口、建议与取舍、有权决定者、受阻部分和可继续工作。建议尚未生效时明确标明。
- 派工/有效变更：完整工作包和授权入口、唯一拥有者、输入版本；触发执行时带 action_id、绑定的负载/版本，重投沿用同 ID；注明追加、替换或抢占。
- 成果交付：产物版本/指纹、原始自测证据、未完成/未知项、指定验收/集成人；可直接引用已有交付卡。
- 决定/验收：可核查的有权决定者及依据、对象/版本、结论、条件和被替代的旧决定；仅写 approved 不授予权限。
- 暂停/恢复：决定来源、范围/版本、已核实与未知的在途状态、接手/恢复负责人；回复收到不等于实际停止。

接收账本沿用既有动作状态、结果/未知项和执行记录；明确重试引用原动作及决定，不另建消息回执账本。运行记录里的 deliveries 表示消息投递，不是成果验收。

不需要动作的普通收悉不回复。正文已有文件时通知定位和变化，相关关键条件仍须可见；完整依据保留在正文和证据中，不设统一字数上限或为压缩丢失反例。接收者在首次有实质内容的回报中体现采用版本及实际动作，不机械增加“复述后等批准”。

### 接口核对示例

```text
用途：接口核对，尚无变更决定
对象：订单汇总接口 R2；消费组向服务组接口负责人核对
重点：固定响应样本中 amount 是字符串，当前 R2 契约写的是数字，联调受阻。
所需动作：核实契约与实际响应，给出需修正对象及原始依据。
相关边界：当前有效要求仍为 R2；本消息不批准变更公共契约或生产发布。
依据：原契约入口及版本、固定响应样本、复现命令。
可继续：其他不依赖 amount 类型的既有任务。
```

### 交付待验收示例

```text
用途：交付待验收
对象：工作包 T12 / 需求 R2 / 产物 C7
重点：amount 返回已按当前契约修正，自测通过；联调尚未验证。
所需动作：指定集成人使用 C7 与当前消费端版本运行原有联调验收。
依据：产物定位及指纹、自测原始输出、实际差异、有效工作包入口。
未完成：联调及结果负责人放行；当前不声明部署完成或验收通过。
```

### 已处理与真正待决示例

```text
已处理：晚到 R1 摘要已失效，继续采用 R2；重复动作 A17 已有完成记录，未重跑。无需主管再次批准这些处理。
待条件：附属核对需要说明文件 v1，现路径为 v2；由该请求的已知发送者补 v1 副本，取得后再核对。主交付不依赖此项。
候选：同伴建议改变统计口径，当前未采纳，不新增实施承诺；仅在有权负责人决定改变需求后更新有效版本。
边界：若 A17 实际结果仍为 unknown，则保留未知和指定对账人，不能按已处理关闭原缺口。
```

示例身份和版本均为虚构。普通消息选择相关字段；正式派工缺少实际范围、验收或授权时不能靠这些简短示例补猜。

如需机器检查，按需使用 [离线 JSON 记录](run-record.md)，不要求把已有任务系统迁移到此格式。

方向和产出字段由负责人结合原要求与实物判断，现有检查器不做语义判定。阶段收敛、辅助支线及恢复使用 [方向与产出](direction.md)，不为每个字段另建文档或审批。

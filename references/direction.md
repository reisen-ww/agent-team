# 长任务的方向与产出

用于长任务拆分、阶段交付、辅助工作膨胀及恢复。目标是尽早发现偏差并限制无效投入，不承诺每一层始终正确。沿用原需求、工作包和进度入口，不建立另一套审批平台。

## 原目标不逐层改写

把下列三类信息明确区分，放入已有共同记录：

- **已确认要求**：PM 要解决的问题、代表性场景、必需结果、禁止事项、验收及有效原文/版本。
- **选择的方法**：经理或执行者选择的工具、架构、依赖和工作顺序；注明选择理由，可在现有权限与成本内替换。
- **待验证假设**：尚未确认的业务解释、技术前提及证伪办法；不能在交接中变成 PM 的硬要求。

每个成员直接读取与其任务有关的原要求和有效决定，而不只接受父节点摘要；不要求所有成员读完整聊天。工作包写清“推进哪条目标、通过什么产物或观察证明”，一行足够时不展开成长文。仅附需求编号不能证明贡献成立。

接手者在首次工作计划中说明自己的理解及关键假设，直属负责人在正常交付中核对；明确且无冲突的工作直接开始，不新增统一的报到、复述批准或逐级 GO。发现任务与原要求冲突时，附具体差异交有权负责人，只停依赖该冲突的部分；不能因为上级派了任务就默认为它符合 PM 意图。

派工负责人在发出首次拆分或实质改动的工作包前，检查组合后是否覆盖原场景、是否把技术偏好升级为要求；这是其本职判断，不增加上级审批。高不确定性的路线先交付一个代表性结果，再据此扩展，而不是把未经验证的拆分一次广播给全队。

## 每层检查不同范围

| 职责 | 方向判断与证据 |
|---|---|
| 用户对接技术经理 | 整体成果是否仍解决 PM 问题；部门目标是否完整、路线与总投入是否值得；核代表性端到端结果和重大假设 |
| 部门主管 | 工作包组合能否交付部门能力，是否遗漏、重复或被辅助支线占据；核跨组接口和领域成果 |
| 执行组负责人 | 拆分是否符合原要求，集成后能否工作；核原文、关键产物及原始证据 |
| 执行者 | 实现与任务是否一致，实际情况是否推翻派工假设；自测并上报矛盾、反例和缺口 |

缺层时明确合并上述职责。所有成员可提出有证据的方向异议；沟通不能变成越权改派。验收需同时判断“工作包仍应做”和“产物满足要求”，不能让大家只把同一个错误拆分执行得更精细。

## 用结果定义阶段

进入一段自主执行前，在已有工作包中明确：**下一项可验收成果、会改变判断的证据、预计交付时间或观察窗、检查负责人、未达到时的动作，以及适用的真实硬边界**。阶段可按完成事件、可计量工作量或时间组织；按任务难度选择，预计值与必须停止的限制分别标明。不能把未计量的额度说成硬限额，也不能因设置了阶段就默认每次继续都需上级批准。

有意义的进展包括：

- 编码：用户场景可运行的增量，或能定位真实缺陷的最小复现与验证。
- 研究：有来源的结论、反证或明确排除的假设；资料数量和抓取量不等于结论。
- 审查：可复现、可处置的发现，或有覆盖范围与证据的无发现结论；问题数量不是成绩。
- 排障、设计或其他任务：已解除的具体阻塞、经代表性场景检验的选择或可使用的交付。

可靠的失败结果可以构成进展，但要说明它排除了什么、下一步因此怎样改变。反复抄同一失败、移动文件、重算未变指纹、补收悉和重写同义方案不构成新进展。不得为提高指标拆碎交付、降验收、隐瞒失败或制造低价值发现。

首次代表性成果应尽早验证，再扩并发；困难任务不必在任意固定分钟数内产出成品，但必须有有界的证据获取目标。阶段结束时，报告先写原目标增加了什么及仍缺什么，再列辅助活动。

## 在时间内提高产出，不制造续期审批

目标是在已确认的时间安排、质量和总资源范围内，尽快取得可验收、可集成使用的成果。未知难度的任务不能靠规定步数或分钟数保证完成；达到预计用时也不允许降低验收、把半成品标成完成。提前满足完成条件就交付，不为用满时间、调用额度或保持成员忙碌而追加工作。

工作包区分三类信息：

| 信息 | 用途 | 到达时的默认处理 |
|---|---|---|
| 预计完成时间 | 帮助安排依赖、识别预估偏差 | 核实际进展和剩余工作；有依据且仍在授权内则继续，不申请额外工具次数 |
| 阶段检查点或观察窗 | 判断当前路线是否值得继续、哪个环节阻塞交付 | 利用已有产物与记录作决定；不自动唤醒上级，也不要求每个成员在同一时刻停工 |
| 明确的硬截止、总预算或权限边界 | 限定已获授权的工作 | 按原约定停止受影响动作，交付部分成果和缺口；延期、续额或扩权由相应有权者决定 |

区分性质和执行能力：用户明确要求的限制即使只能靠代理遵守，仍是必须遵守的指令；是否存在宿主强制计时/计费门禁另外说明。没有执行能力不能声称会自动截停，也不能把强制能力缺失解释为可以继续超额。

到达普通检查点时，由当前职责负责人结合实际情况处理：

| 实际情况 | 采取的动作与责任 |
|---|---|
| 已满足完成与验收条件 | 交付或转入约定验收，释放容量 |
| 有实质进展，剩余工作明确，资源仍在授权内 | 执行者继续，更新现有记录中的剩余工作和预估；不为正常继续新增请批回合 |
| 新证据推翻了实现假设 | 在职责范围内调整方法，记录依据并做必要验证；涉及已确认目标/公共契约变化的部分交有权者 |
| 同一失败反复出现，没有改变下一步判断的新证据 | 停止该无效尝试；能在既定边界内换路线就换，不能局部解决则带证据交直属负责人 |
| 外部依赖或决定暂不可得 | 明确缺什么、谁能解除、何时或由什么事件恢复；继续不依赖它的工作，不用重复查询填充等待 |
| 接近或触及真实硬边界 | 尽早交具体缺口及可用成果，按授权处理后续；不能等越界后再把产出当作自动追认 |

正常继续的决定不要求再造一份报告。用已有工作包、产物、测试输出或证据索引说明进展及下一步，留到正常交付/约定汇总时由直属负责人核对。只有状态影响了其他成员、出现真实阻塞或需要有权者改变安排时才发出相应通知。主管的例行检查沿用已约定方式，不以这些条款自动创建后台任务。

继续工作需要看到实际成果或会改变下一步判断的信息。代码量、文件数量、消息量、重述计划以及把同一问题反复标成“接近完成”不能支持不断顺延。负责人也受这一要求约束：阶段迟迟没有约定成果时，应判断是否错误拆工、辅助工作膨胀、方法失效或资源不足，并决定简化、复用、换路、调配或结束该支线。可在原授权内完成的调整自行处理；需要改变确认的范围、总成本或硬截止时才交相应决定者。保留最初预估与实际经过时间，不通过移动日期抹掉偏差。

### 具体判断示例

- 编码超过原预估，但已完成核心逻辑、正在验证明确的剩余边界，且总资源足够：继续并更新依赖方的预期；无需申请更多工具次数。自测通过后仍进入原有验收，不把继续工作变成自我放行。
- 排障尚未修复，但新复现把问题定位到特定输入或状态变化：这是可说明价值的进展，可在授权内开展相应修复。若只是反复运行同一命令并看到同一错误，则不能据此延长原路线。
- 研究已取得能回答问题的证据，剩余不确定性不影响约定结论：整理并交付，不能为了填满观察窗继续收集同类资料。若缺关键证据，明确其影响并做针对性核查，不凭截止临近补造结论。
- 等待构建、服务或外部决定：等待计入交付经过时间，另外说明等待原因和可做的独立工作，不能一概判作执行者空转；依赖未变时重复催促或重启不算进展。
- 硬截止已经到达但任务仍不完整：按停止条件交付已可用部分和缺口，明确未完成项；不能默默延期，也不能降标准宣称完成。

## 辅助工作何时收敛

新增工具、测试设施、管理流程或调查支线，先说明它解除哪个具体阻塞、最小足够结果、允许投入及退出/换路条件。它们可以有价值，但不能悄悄代替本轮成果。不要为假设的未来规模提前建设本轮不需要的通用设施。

到约定检查点仍未得到目标成果或改变判断的新证据，当前职责负责人应比较继续、简化、复用、换路与停止该支线的成本，记录具体决定。继续需有新的依据和下一检查点，不能只写“再完善一下”。反复出现同一无进展状态或依赖链持续增长时，先停止扩张该支线，在已有决定权内收敛；超出该职责的决定才升级。触及真实硬额度按其停止条件执行，不以换会话、改名或“仍在第一轮”重置投入。

检查点也覆盖尚未首交付的在办任务；执行者发现阻塞或无进展触发条件时应主动保留部分成果并交所需决定，不能等主管询问。有进展的普通预估偏差按上节继续，不一律上报为阻塞。原负责人不得仅靠不断顺延检查点自行续额；依赖与关键决策未变化时，等待必须有明确的恢复人和条件。

区分 PM/宿主的硬限制与代理自行选择的实现流程。前者必须遵守；后者可在现有授权内精简。安全检查须对应实际风险和最小证据，不追求证明一切都绝对安全。确实需要新权限才能推进时集中说明，不能绕过限制，也不能靠不断审查辅助材料回避真实阻塞。

只暂停受影响的支线；仍有明确价值且依赖就绪的工作继续。核实被停执行者、资源和文件状态后再接手，保留可复用成果与首次失败，不把“停止无效工作”变成删除原件或全队无期限等待。

## 校准时点与恢复

在首次代表性成果、扩大并行、关键假设被推翻、依赖/预算显著增长、阶段交付，以及压缩/交接后恢复时校准。恢复先核对有效目标和原始决定，再核进度及当前产物；摘要、检查器通过或旧主管结论均不能覆盖原文。正常压缩由当前负责人恢复，不机械新增独立审查。

日常检查由直属负责人承担。顶层只处理已约定的关键阶段、整体路线、跨域争议与需 PM 决定的变化；阶段边界不自动创建计时器或轮询。缺少真实后台调度时采用完成事件/主动交付，不能声称已按时巡检；需要无人值守的期限停门时先核实宿主能力。

有证据表明同一假设在各层传播时，按已有权限安排一次覆盖原目标、拆分和实际成果的独立挑战；不要只审下层代码。默认仍不为逐次员工交付创建审查树。

纠偏时定位最早失真的假设/决定，更新相关工作包和受影响验收，核实通知与接续版本；不把全队重做当默认办法。记录/链接不可达或仍指向旧目标时修复入口，关键缺口未恢复前只暂停依赖它的操作。

## 验证规则是否有效

离线字段检查只能发现部分结构矛盾，不能自动理解目标是否正确。情境推演只能说明面对给定材料的选择；短阶段真实实施只能证明该次场景，不能冒充数日连续运行、真实压缩或生产保证。

先用 [方向与产出验证](../examples/direction-check/README.md) 检查错误拆分、辅助依赖膨胀、陈旧摘要、测试全绿但目标缺失，以及正常工作能否继续。随后在实际项目选有界阶段观察。保持任务、质量和资源范围可比，优先比较取得可用成果的总时长、实际费用、主管介入、等待、返工及误停正常工作的情况；命令/调用数只作为解释行为的辅助证据，不直接换算为费用或效率。没有同条件对照不宣称节省比例。复核实际动作和产物，不给遵守规则的措辞打分。

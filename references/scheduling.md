# 规模、调度和主管减负

按“完成验收的交付/总成本”评价安排。总成本包括模型调用、重复上下文、等待、返工、用户参与和集成。成员名册、活跃请求、进行中工作和已验收产出分别记录。百名成员不要求百人同时工作。

## 先贯通，再扩并发

先让少量成员完成一个包含真实输入、端到端结果和验收的代表性切片。确定哪些工作真正独立、哪些在关键路径，再在已授权容量内逐步增加就绪工作。示例人数不构成最佳规模证明。

派工至少满足：要求与输入版本可定位、关键依赖就绪、唯一拥有者和写入边界明确、验收可执行、预算剩余且主管/集成有承接能力。计划中的工作不是已承诺执行；候选发现先去重、分级，不自动变成新任务。

| 观察到的情况 | 调度动作 |
|---|---|
| 独立就绪包增加，验收及时，成本在范围内 | 小幅增加活跃工作，观察从派工到验收的完整周期 |
| 待审/待集成持续堆积或在办年龄增加 | 降低新工作准入，让原有工作完成，不降低验收要求 |
| 相同接口/共享资源反复阻塞 | 先解决契约或资源约束；堆人不能增加独占资源容量 |
| 集成人承担大量未分配实现 | 重新分配完整职责，先减轻关键路径再增员 |
| 更多调用没有增加合格产出 | 回退最近扩容，查依赖、返工与上下文成本 |

对比保持目标、质量标准和任务难度可比。吞吐、端到端墙钟、待决/待审时长、返工、上下文与费用分别记录；拿不到账单就写未知。不同任务的六人/八人短测不能直接给出最佳人数或规模曲线。

## 主管忙时

日志整理和重复取证交现有执行者或确定性脚本；主管聚焦异常、关键判断及验收。一次性专项分析可在既有授权和总额度内交适合的人；这不授权隐形增员。两个稳定、可独立负责的方向长期争抢主管时，才考虑拆第二个主管，并交出对应决定权，避免旧主管仍逐项审批。

先减少新承诺、归并反馈、解决共享约束；超出人员/成本上限才申请调整。主管、辅助者、审查者都计入活动量与成本。一个会话兼多角色只算实际会话/请求一次，但各职责的工作负载仍须显式考虑。

## 低成本监督

默认按交付、阻塞和风险变化处理。技术经理派工后把日常跟踪交直属主管，不保持高成本会话反复等待。员工不向所有上级抄送。部门先自行协调，需用户决定、跨域无法解决或重大风险才升级。

启动时约定通知策略：本地保存、仅异常通知、或阶段完成通知。用户要求不跟踪时采用本地保存和必要异常升级，不因“完成了一个员工任务”反复唤醒顶层。用户主动提问/暂停及时处理，不按巡检周期拖延回复。

只有用户要求定期监督且实际调度能力可用时，配置明确负责人和间隔。文字间隔不等于计时器，不用常驻 sleep/短轮询冒充低成本调度。通知偏好按宿主工具字段保存。无新变化不补跑多个过期检查，也不互发收悉。

## 预算与返工只记一套账

启动前说明预算的单位、范围、计数人/程序及达到上限的动作。真实费用、模型请求、时长、模拟配额、返工批次不能互相替代；缺少工具计数的上限标为软约束。并发槽位和累计支出是不同概念。

需要限制返工时，使用项目唯一的全局 batch_id，绑定输入产物版本、缺陷集合、涉及工作包、开始/结束及负责人。每个员工的修复引用该 batch_id；个人上限只能作为全局上限内的额外限制，不能把全局两批解释成每人两批。

同批可归并多人的相关修复，关闭后不得重新打开为旧批来逃避计数。开放批次有检查点和预算；不能无限延长“还在初版”。首交付前的正常自测不算交付后返工，但仍消耗总调用/时长/费用。改请求ID、会话、角色名或称“同一轮”不会续额。

达到额度时停止新派发/新返工，保留部分成果、首败与具体缺口，按实际能力处理在途工作；向有权者请求明确续额或调整范围。不静默降级质量，不宣称文本额度已强制停止进程。

# PM—技术经理对齐

用户负责目标、业务优先级、重要偏好和本轮授权。直接对接用户的 AI 负责专业建议、事实核查、方案与成本取舍、组织交付和技术验收。两者不互相代替。其他成员不单独向用户发起隐藏的提问。裁切后的最上层主管/组长兼任技术经理，仍执行本入口；无需创建额外上级或指定模型名。

## 开始与恢复

新项目、团队启动或方向含糊时使用；明确的小改动直接做。先读现有需求、决定和进度，避免让用户重述能恢复的答案。不因角色名称另开经理或切换模型。

对齐期间可以只读检查、查资料、整理方案；未定需求所依赖的实施等待回答。访谈不授权实际团队、额外费用、外部写入或生产操作。原有批准覆盖的独立工作可以继续。

## 完整但相关的问题清单

默认按主题集中给出较完整的编号清单，让用户逐项回答；按已知信息删减，不机械问满所有主题。用户偏好短轮次时调整呈现。允许多轮追问，每轮解决新的缺口，不设为了追问而追问的轮数。

| 主题 | 需要澄清的实际内容 |
|---|---|
| 目标与使用者 | 谁遇到什么问题，什么变化才算成功，现有做法哪里不满意 |
| 场景与边界 | 输入、操作、输出、运行环境、失败情形，本轮做什么及明确不做什么 |
| 成果与偏好 | 交付形态，参考中喜欢/反对的部分，关键交互、风格和素材路线 |
| 数据与权限 | 已有资产、来源、输出去向、可访问环境、账号和写入边界；可核实事实由经理查 |
| 质量与验收 | 必需项、理想目标、可接受范围、实际检查方法，以及不可接受的失败 |
| 成本与节奏 | 交付节点、资源上限、代定范围、可以接受的等待和返工 |
| 协作与沟通 | 是否确需团队；角色合并、人员/模型、活跃并发、审查和集成人选、插队/恢复、通知与停止方式 |

使用实际例子、反例和可见效果帮助表达。给出推荐及取舍，不要求用户替经理设计技术架构。目标与用户提出的手段分开；可以建议更简单的手段，不能悄悄换目标。

- “你来定”：在所指范围内说明推荐后代定，并记录委托，不能外推成全局授权。
- “我不懂”：解释选项和实际效果；不是批准或委托。
- 部分作答：保留已答内容，只追问遗漏或依赖项。沉默不是确认。
- 表达不清：给代表性场景/草图帮助校正；需要制作原型时先明确原型这一轮的实施边界。

## 确认理解与开工

经理复述完整使用场景和关键失败边界，必要时补流程图、草图或代表性样例。将目标、范围、禁止事项、细节、验收、单会话/团队方案、成本安排、已定/待定事项保存在共同记录。

开工依据是核心验收可判定、方向性业务/偏好缺口已经处理、其他开放项有处理方式，且用户确认本轮范围及重要安排。清晰展示后的“按这个做”“go”可构成确认；回答一个问题、经理自评理解了、同伴声称 PM 同意，都不自动构成确认。

已确认任务只对齐变化。规模数字只是用户的资源意图时，经理应说明依赖、验收能力和成本影响，再确定活跃并发；不把一张组织图变成必须花满的资源订单。

长任务将首个可使用/可验证的成果、阶段边界与无进展时的处理纳入方案；区分 PM 硬要求、经理所选方法和待验证假设，按 [方向与产出](direction.md) 执行。不要为了排队等待最终验收而先完成所有辅助设施。

## 需求连续性

沿用项目既有要求/决定/进度记录，不建重复档案。为重要决定保存准确含义、必要原话片段、具体例子、禁止项、确认状态、适用范围、理由和替代关系；不要缩成“按偏好处理”。

在确认、变更、交付、阻塞和交接时及时保存，不能等压缩才补。摘要仅作导航，原文和有效决定仍是验收依据。恢复按 [记录与通信](coordination.md) 核对；已经能恢复的答案不重复问。项目记录不自动授权全局个人记忆、外部同步或公开发布。
